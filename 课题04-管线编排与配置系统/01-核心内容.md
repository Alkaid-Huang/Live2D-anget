## 3. 核心模型：从"一坨代码"到"流水线"

### 3.1 第一性原理：为什么需要管线？

**【类比/解释】** 想象一家汽车工厂。如果一个人从头到尾造一辆车——焊车身、装发动机、喷漆、装座椅——他得花 10 小时。但如果分成 4 个工位，每个工位只做一件事，4 辆车同时在不同工位上流动，每 2.5 小时就出一辆车。这就是**流水线**——把一个大任务拆成多个小阶段，每个阶段只做一件事，阶段之间用"传送带"连接。

Echo 的语音对话也是一条流水线：

```
音频输入 → ASR(语音转文字) → LLM(生成回复) → TTS(文字转语音) → 音频输出
```

**如果不用管线（全写在一个函数里）会怎样？**

```python
# ❌ 反面教材：一个函数干所有事
async def handle_conversation(audio_data):
    text = await asr(audio_data)      # 等 1 秒
    reply = await llm(text)           # 等 2 秒
    audio = await tts(reply)          # 等 1 秒
    send(audio)                       # 总共 4 秒
```

问题：
- **无法并行**：LLM 在思考时，ASR 完全闲着，浪费资源
- **无法扩展**：想加一个"翻译"环节？得改这个函数
- **无法替换**：想换 ASR 模型？得到处找 `asr()` 调用点

**用管线后：**

```
ASR阶段          LLM阶段          TTS阶段
  │                │                │
  ▼                ▼                ▼
[处理音频]──Queue──→[生成回复]──Queue──→[合成语音]──Queue──→[输出]
  │                │                │
  └─ 不等 LLM      └─ 不等 TTS      └─ 不等 ASR
     立刻处理下一条    立刻处理下一条    立刻处理下一条
```

每个阶段只管自己的事，通过 `asyncio.Queue`（传送带）把结果传给下一个阶段。LLM 在思考时，ASR 可以继续处理下一句话。

### 3.2 第一性原理：为什么需要 ServiceContext？

**【类比/解释】** 想象你去医院看病。如果没有分诊台，你得自己找每个科室——内科在 3 楼、检验科在 5 楼、药房在 1 楼。每次换个科室，你都得重新找路。**ServiceContext 就是医院的分诊台**——它知道所有科室在哪里，你只需要问它一次，它就能告诉你所有服务的位置。

不用 ServiceContext 时（全局变量地狱）：

```python
# ❌ 反面教材：到处都是全局变量
asr_engine = WhisperASR()
tts_engine = EdgeTTS()
llm_engine = OllamaLLM()

async def handle_message(msg):
    # 这个函数怎么拿到 asr_engine？靠全局变量。
    # 如果有 2 个用户想用不同的 ASR？全局变量只有一份，做不到。
    text = await asr_engine.transcribe(msg.audio)
    ...
```

问题：
- **多用户冲突**：用户 A 用 Whisper，用户 B 用 sherpa-onnx，全局变量只有一份
- **测试困难**：测试时要 mock 全局变量，容易污染其他测试
- **生命周期混乱**：谁负责创建？谁负责销毁？没人知道

**【事实】** Open-LLM-VTuber 的 `ServiceContext` 是一个纯数据持有类，每个 WebSocket 连接实例化一个新的。它持有 `asr_engine`、`tts_engine`、`agent_engine`、`live2d_model` 等所有服务实例的引用。[$TRAE_REF](https://github.com/Open-LLM-VTuber/Open-LLM-VTuber/blob/main/src/open_llm_vtuber/service_context.py)

### 3.3 第一性原理：为什么需要配置驱动？

**【类比/解释】** 想象你买了一台洗衣机，面板上有 10 个按钮。如果每次洗衣服都要拆开机器重新接线来选"轻柔模式"，你肯定崩溃了。正确做法是：**机器内部逻辑不变，你只需要按按钮**。配置文件就是那些"按钮"——不改代码，只改配置，就能切换行为。

不用配置驱动时：

```python
# ❌ 反面教材：选择写死在代码里
asr = WhisperASR(model="small")  # 想换 sherpa-onnx？改代码、重启服务
```

用配置驱动后：

```yaml
# conf.yaml —— 改这个文件，不改代码
asr:
  model: "whisper"    # 想换？改成 "sherpa_onnx" 就行
  delay: 0.2
```

**【事实】** Open-LLM-VTuber 的所有组件选择和行为都通过 `conf.yaml` 控制，使用 Pydantic 模型进行层级验证。用户可以在不修改代码的情况下重新配置整个系统。[$TRAE_REF](https://deepwiki.com/Open-LLM-VTuber/open-llm-vtuber.github.io/3-configuration-system)

## 4. 关键概念与例子

### 4.1 asyncio.Queue —— 阶段间的传送带

`asyncio.Queue` 是一个**异步安全的先进先出队列**。一个协程往里放数据（`put`），另一个协程从里取数据（`get`）。如果队列空了，`get` 会自动等待，不占 CPU。

```python
import asyncio

queue = asyncio.Queue(maxsize=10)  # 最多放 10 个数据

# 生产者：往队列放数据
async def producer(queue):
    for i in range(3):
        await queue.put(f"数据{i}")  # 队列满了会自动等待
        print(f"放入: 数据{i}")

# 消费者：从队列取数据
async def consumer(queue):
    for _ in range(3):
        item = await queue.get()     # 队列空了会自动等待
        print(f"取出: {item}")
        queue.task_done()            # 告诉队列"这个数据处理完了"

async def main():
    await asyncio.gather(producer(queue), consumer(queue))

asyncio.run(main())
# 输出：
# 放入: 数据0
# 取出: 数据0
# 放入: 数据1
# 取出: 数据1
# 放入: 数据2
# 取出: 数据2
```

**关键方法速查表：**

| 方法 | 作用 | 参数 | 返回值 | 会等待吗？ |
|------|------|------|--------|-----------|
| `await queue.put(item)` | 往队列放一个数据 | `item`：任意对象 | `None` | 队列满时等待 |
| `await queue.get()` | 从队列取一个数据 | 无 | 队列中的下一个数据 | 队列空时等待 |
| `queue.task_done()` | 告诉队列"取出的数据处理完了" | 无 | `None` | 不会 |
| `await queue.join()` | 等待队列中所有数据都被处理完 | 无 | `None` | 有未处理数据时等待 |
| `queue.qsize()` | 查看队列里有多少个数据 | 无 | `int` | 不会 |
| `queue.maxsize` | 队列最大容量 | 属性 | `int` | — |

**`maxsize` 的作用——背压控制：**

如果生产者比消费者快，队列会越来越大，最终内存爆炸。设置 `maxsize=10` 后，队列最多放 10 个数据，满了之后生产者的 `put()` 会自动等待，等消费者取走一个才能继续放。这叫**背压**（backpressure）——强迫生产者慢下来。

### 4.2 dataclass —— 轻量级数据容器

`dataclass` 是 Python 的一个装饰器，用来快速创建"只存数据"的类。不用手写 `__init__`，Python 自动生成。

```python
from dataclasses import dataclass, field

@dataclass
class ServiceContext:
    """集中管理所有服务实例和配置 —— 分诊台"""
    config: dict = None          # 从 YAML 加载的配置
    input_queue: asyncio.Queue = None   # 阶段1→2 的传送带
    asr_queue: asyncio.Queue = None     # 阶段2→3 的传送带
    llm_queue: asyncio.Queue = None     # 阶段3→4 的传送带
    output_queue: asyncio.Queue = None  # 阶段4→输出的传送带

# 创建实例
ctx = ServiceContext()
ctx.config = {"asr": {"delay": 0.1}}
ctx.input_queue = asyncio.Queue(maxsize=10)
```

**`@dataclass` 做了什么？**
- 自动生成 `__init__(self, config=None, input_queue=None, ...)`
- 自动生成 `__repr__`（打印实例时显示所有字段）
- 你只需要声明字段名和默认值

**【事实】** Open-LLM-VTuber 的 `ServiceContext.__init__` 手动声明了 `self.config`、`self.asr_engine`、`self.tts_engine`、`self.agent_engine` 等十余个字段。我们用 `dataclass` 可以更简洁地实现同样的效果。[$TRAE_REF](https://github.com/Open-LLM-VTuber/Open-LLM-VTuber/blob/main/src/open_llm_vtuber/service_context.py)

### 4.3 PyYAML —— 读取配置文件

```python
import yaml

# 读取 YAML 文件
with open("conf.yaml", "r", encoding="utf-8") as f:
    config = yaml.safe_load(f)

# config 现在是一个 Python 字典
# conf.yaml 内容：
#   pipeline:
#     asr:
#       delay: 0.2
#       enabled: true
#
# config = {"pipeline": {"asr": {"delay": 0.2, "enabled": True}}}
```

**关键方法：**

| 方法 | 作用 | 参数 | 返回值 |
|------|------|------|--------|
| `yaml.safe_load(stream)` | 把 YAML 字符串/文件流解析为 Python 字典 | 文件对象或字符串 | `dict` / `list` / `str` 等 |
| `yaml.dump(data, stream)` | 把 Python 对象序列化为 YAML 字符串 | `data`：对象，`stream`：文件对象 | `str` 或 `None` |

**为什么用 `safe_load` 而不是 `load`？** `load` 能执行任意 Python 代码（安全风险），`safe_load` 只解析基本数据类型（dict/list/str/int/float/bool/None），安全。

### 4.4 完整管线架构图

```
conf.yaml（配置文件）
    │
    ▼
┌─────────────────────────────────┐
│        ServiceContext           │  ← 集中管理所有服务和队列
│  ┌───────────────────────────┐  │
│  │ config: {从YAML加载}      │  │
│  │ input_queue: Queue        │  │
│  │ asr_queue: Queue          │  │
│  │ llm_queue: Queue          │  │
│  │ output_queue: Queue       │  │
│  └───────────────────────────┘  │
└─────────────────────────────────┘
    │
    │  启动 4 个协程任务
    ▼
┌──────────┐  asr_queue  ┌──────────┐  llm_queue  ┌──────────┐  output_queue  ┌──────────┐
│  输入阶段 │ ─────────→ │ ASR阶段  │ ──────────→ │ LLM阶段  │ ────────────→ │ 输出阶段  │
│          │             │          │             │          │                │          │
│ 产生模拟  │             │ 把"音频"  │             │ 把"文字"  │                │ 打印结果  │
│ 音频数据  │             │ 转"文字"  │             │ 转"回复"  │                │          │
└──────────┘             └──────────┘             └──────────┘                └──────────┘
    │                        │                        │                          │
    └──── asyncio.TaskGroup 管理这 4 个协程的启动和取消 ────┘
```

## 5. 常见坑

### 坑 1：忘记 `queue.task_done()`

```python
async def consumer(queue):
    while True:
        item = await queue.get()
        print(item)
        # ❌ 忘记 task_done()
        # 如果主协程用 await queue.join() 等待，会永远卡住
```

### 坑 2：Queue 在不同事件循环中创建

```python
# ❌ 在模块顶层创建 Queue，此时事件循环可能还没启动
queue = asyncio.Queue()  # Python 3.10+ 会在第一次使用时报错

# ✅ 在 async 函数内部创建
async def main():
    queue = asyncio.Queue()  # 正确：此时事件循环已运行
```

### 坑 3：消费者死循环无法退出

```python
async def consumer(queue):
    while True:           # ❌ 永远不会停
        item = await queue.get()
        print(item)

# ✅ 用"哨兵值"（sentinel）通知消费者退出
async def consumer(queue):
    while True:
        item = await queue.get()
        if item is None:  # 收到 None 就退出
            break
        print(item)
```

### 坑 4：配置文件路径错误

```python
# ❌ 相对路径取决于"运行时的工作目录"，不可靠
with open("conf.yaml") as f:  # 从别的目录运行就找不到

# ✅ 用 __file__ 锚定到脚本所在目录
import os
script_dir = os.path.dirname(os.path.abspath(__file__))
config_path = os.path.join(script_dir, "conf.yaml")
with open(config_path) as f:
    config = yaml.safe_load(f)
```

### 坑 5：TaskGroup 中的异常会导致整个管线崩溃

```python
async with asyncio.TaskGroup() as tg:
    tg.create_task(input_stage(ctx))
    tg.create_task(asr_stage(ctx))
    tg.create_task(llm_stage(ctx))
    tg.create_task(output_stage(ctx))
# 如果任何一个阶段抛出未捕获异常，TaskGroup 会取消所有其他任务
# 这通常是好事（一个环节崩了，整条线都该停），但要确保异常被正确处理
```

## 6. 你的任务：实现 4 阶段模拟管线

> 你需要实现一个配置驱动的 4 阶段异步管线。4 个阶段通过 `asyncio.Queue` 串联，配置通过 YAML 文件控制每个阶段的延迟和处理行为。

### 任务说明

| 阶段 | 输入 | 输出 | 模拟行为 |
|------|------|------|---------|
| 输入阶段 | 配置中的 `items` 列表 | `{"audio": "音频N"}` | 产生 N 条模拟音频数据，放入 `input_queue` |
| ASR阶段 | `{"audio": "音频N"}` | `{"text": "文字N"}` | 把"音频"转成"文字"，延迟由配置控制 |

| 输出阶段 | `{"reply": "回复N"}` | 打印到控制台 | 接收并打印结果，收到 `None` 时结束 |
