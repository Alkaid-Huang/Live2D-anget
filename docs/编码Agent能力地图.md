## 二、五条能力 → 组件 → 度量

### 1. 理解庞大代码库（检索 + 上下文压缩）

| 子能力 | 工程做法 | 度量 |
|--------|---------|------|
| 建索引 | tree-sitter 解析 AST，抽取函数/类/符号与调用关系；按文件+符号粒度切片 | 索引覆盖率、切片粒度合理性 |
| 检索 | 混合检索：BM25（词面）+ 向量（语义）→ **RRF 融合** → Reranker 精排；再叠加"仓库结构信号"（目录/依赖） | recall@k（能否召回真正要改的文件） |
| 上下文压缩 | token 预算分配（系统/检索/工具结果各占多少）；层级摘要（文件级→模块级）；行号锚点替代整文件；工具输出截断与摘要 | 上下文 token 数、无效上下文占比 |
| 定位 | 先定位再修改（localize → repair → validate 三段式，Agentless 思路） | 文件级/行级定位准确率 |

### 2. 复杂工具调用（ACI：Agent-Computer Interface）

| 要点 | 做法 |
|------|------|
| 工具粒度 | 少而正交：`view`（带行号）/`search`/`edit`/`run`，避免几十个碎工具让模型选错 |
| 编辑格式 | 搜索-替换（带上下文锚点）比整文件重写安全；`aider` 的 diff 格式值得研究 |
| 编辑后校验 | 每次编辑后跑语法/lint（**失败就把错误回灌给模型**，不等测试阶段） |
| 模糊匹配 | 匹配不唯一时**拒绝执行**并提示，而不是猜 |
| 度量 | 工具调用成功率、编辑应用率（edit apply rate）、无效编辑次数 |

### 3. 多轮反思与修复

- 循环骨架：`跑测试 → 解析失败 → 定位 → 改 → 再跑`，加**轮次与预算上限**（防止无限烧钱）
- 反思形态：把完整失败输出作为证据回灌；对同一错误重复两次就换策略（换检索词/换文件）
- 度量：**pass@1**（一次提交通过率）、平均修复轮次、**回归引入率**（原本通过的测试是否被弄坏）

### 4. 长任务的状态与记忆

| 要素 | 做法 |
|------|------|
| 任务状态机 | `planning → editing → testing → done/failed`，状态可恢复 |
| 变更日志 | 每次改动记录 **diff + 理由**（"为什么改"往往比"改了什么"更关键） |
| 上下文管理 | 滚动摘要 + 检索补充，避免把所有历史塞进窗口 |
| 检查点 | 每个里程碑一次 git commit / stash，支持回到任意点 |
| 度量 | 中断后可恢复性、重复犯错率、长任务（>20 步）成功率 |

### 5. 安全：沙箱、权限、回滚

| 层面 | 做法 |
|------|------|
| 执行隔离 | 容器/微虚拟机（Docker 起步），限定工作目录挂载 |
| 权限分级 | 读操作默认允许；写文件限定仓库内；`rm`/`git reset --hard`/网络访问需显式授权 |
| 网络 | 默认关闭，白名单（包管理器/文档站）按需开放 |
| 回滚 | git 检查点 + 一键 `git restore`；对不可逆操作先 dry-run |
| 度量 | 危险操作拦截次数、回滚成功率、越界修改（改动仓库外文件）次数 |

### 6. 评估（这一步决定"能不能拿出去讲"）

| 维度 | 指标 |
|------|------|
| 正确性 | 测试通过率（pass@1 / pass@k）、SWE-bench Verified 子集或自建 20 题 |
| 补丁质量 | diff 大小、是否只改必要文件、lint/typecheck 通过、人工评审打分 |
| 安全性 | 是否引入漏洞（Semgrep/CodeQL 扫描对比）、是否泄露密钥、是否越权操作 |
| 成本 | token 消耗、模型调用次数、墙钟时间 |
| 可靠性 | pass^k（同一任务重复 k 次的稳定性），而不是只看最好一次 |

## 四、落地方案：Mini CodeAgent（推荐）

### 4.1 选题：**让 Agent 去修 Echo 自己的 bug**

为什么这个选题好：

- 仓库小、结构清晰，索引与检索能在几百毫秒内完成，适合做**对照实验**
- 有**现成的 ground truth**：我们修过的真实 bug（CUDA 降级、silero Tensor/采样率、批处理编码）
  + 可以再注入 10 个 bug 作为测试集
- 评测客观：跑 `pytest` 就知道修没修好，且能统计"有没有弄坏别的测试"
- **面试叙事极强**："我写了个编码 Agent，它修的第一个项目是我自己写的语音助手。"

### 4.2 最小工具集（4 个）

| 工具 | 说明 | 安全约束 |
|------|------|---------|
| `view` | 带行号读文件 / 列目录 | 仅仓库内路径 |
| `search` | 正则/符号检索（内部调 rg 或纯 Python 实现） | 只读 |
| `edit` | 搜索-替换（要求上下文唯一），改完立刻跑语法检查 | 仅仓库内、写前备份 |
| `run` | 在**临时 git worktree** 里跑 `pytest -q`（可选 Docker） | 白名单命令、超时、输出截断 |

外加两个非工具动作：`git diff`（生成补丁报告）与 `rollback`（回到检查点）。

### 4.3 循环与预算

```
任务(issue 描述 + 失败测试)
  → 定位（search/view，最多 N 次）
  → 修改（edit，改一次校验一次）
  → 验证（run pytest）
  → 失败？→ 反思（把失败输出 + 已改内容作为证据）→ 回到定位
  → 通过？→ 输出 diff + 变更理由 → 结束
预算上限：最多 K 轮、最多 M 次工具调用、最长 T 分钟
```

### 4.4 评测集与指标

- 任务集：10 个注入 bug（每个都给"失败测试 + 一句话现象"）+ 之前修过的真实 bug 复现
- 指标：**pass@1**、平均轮次、平均 token、回归引入率、越界修改率、危险命令拦截次数
- 输出：`benchmarks/codeagent_results.md`（和 Echo 的延迟基线同一个风格）

### 4.5 工作量估算（按你每天 2 小时的节奏）

| 阶段 | 内容 | 预计 |
|------|------|------|
| 1 | 工具集 + 沙箱（worktree + 白名单）+ 单测 | 2–3 天 |
| 2 | 循环 + 反思 + 预算控制 | 2 天 |
| 3 | 注入 bug + 评测 harness + 指标报表 | 2 天 |
| 4 | 文档 + 交互演示（命令行）| 1 天 |
| 可选 | 混合检索（BM25+向量+RRF）与上下文压缩对比实验 | +3–5 天 |

## 五、两条路线，怎么选

> **2026-09-13 更新**：已确定采用"集成进项目"的方式——
> 产品侧设计见 `echo-voice-assistant/docs/编码Agent集成设计.md`（两套工具包 + 沙箱 + 评测 + 分阶段计划），
> 学习侧按阶段记录见 `docs/学习笔记-编码Agent.md`。

**路线 A：Mini CodeAgent（推荐，1.5–2 周）**
在 Echo 之外开一个小项目（同一套 Agent 内核），做"给 Echo 修 bug 的 Agent"。
优势：与现有资产强复用、有客观评测、面试叙事强。
代价：Echo 的 Live2D（M3）会往后推。

**路线 B：继续 Echo + 深读源码（不新开项目）**
把编码 Agent 能力当学习线：读 SWE-agent/OpenHands/aider 源码，写对比与设计笔记，
面试时讲得清 ACI、沙箱、评测。优势：不动现有交付节奏；代价：简历上少一个硬产出。

**我的建议**：如果你确定投"Agent / 大模型应用"方向，选路线 A——但先把 Echo 的 M3 做到"能演示"再切，
否则两个项目都半成品。如果面试就在两周内，先保住 Echo 的演示闭环，路线 B 作为并行学习。
