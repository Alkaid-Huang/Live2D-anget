## 3. 核心模型

### 3.1 调试五步法（本课骨架）

```
复现 → 提出假设 → 收集证据 → 定位根因 → 修复 + 防回归
 │         │            │            │            │
 │   列出所有可能    用日志/断点    排除法锁死   改对 + 写测试拦住
 │   的原因         /二分/对照      唯一根因
 │                                        │
 └──────── 证据不足 → 回到"提出假设"重新来 ──┘
```

**【类比/解释】** 调试不是"猜"，是**破案**：现象是案发现场，假设是嫌疑人名单，证据是监控录像。破案靠的是证据排除嫌疑人，不是靠直觉指认。

### 3.2 现象 ≠ 根因

| 层次 | 是什么 | 例子（06.2 真实发生） |
|------|--------|----------------------|
| 现象 | 你看到的不对劲 | 测试报 `TypeError: takes 1 positional argument` |
| 假设 | 可能的原因（可以有好几个） | ① 工厂签名错了 ② 参数传错了 ③ 调用方式不对 |
| 证据 | 能排除/确认假设的事实 | 看报错栈 → 问题在 `create_vad(vad_type, params)` 这一行 |
| 根因 | 唯一确定的原因 | `params` 字典没解包，被当成位置参数 |

### 3.3 三类 bug 模式（本课实战对象）

| 模式 | 特征 | 典型例子 | 为什么测试抓不到 |
|------|------|---------|-----------------|
| **静默失效** | 不报错，但行为悄悄变错 | 分贝公式系数 20 写成 10 | 测试只断言"范围"，没断言"精确值" |
| **契约不匹配** | 两处代码对"约定"理解不一致 | 配置字符串写 `silero`，判断用 `silero_vad` | 测试只检查字段存在，没检查参数透传 |
| **边界逻辑** | 判断条件差一点（off-by-one） | `>= required_hits` 写成 `>= required_hits + 1` | 测试没覆盖这条代码路径 |

## 4. 关键概念与例子

### 4.1 复现：稳定触发 bug 的最小条件

复现不是"多跑几次碰运气"，而是找到**最小、稳定**的触发条件。

```python
# 本课的复现脚本已经给你写好了
python reproduce.py
```

运行后你会看到三个"不对劲"的输出。你的第一步就是观察它们、描述它们（写下来），这就是**复现 + 记录现象**。

### 4.2 工具：调试器 vs print

```python
# print 调试（你会很想用，但先看看缺点）
print(db)          # 只能看这一个值，要自己决定在哪打

# 调试器（本课要求至少用一次）
breakpoint()       # 程序停在这里，进入 pdb 交互
# 常用命令:
#   n  下一步（不进入函数）
#   s  进入函数
#   p db           查看变量
#   c  继续运行到下一个断点
#   q  退出
```

**【事实】** Python 内置的 `breakpoint()` 在 Python 3.7+ 可用，等价于 `import pdb; pdb.set_trace()`。[来源：Python 官方文档 built-in functions（2026-08-13 参考）]

调试器相对 print 的优势：不用改代码就能看任何变量、可以单步走、可以停在条件满足的那一刻。**print 是"猜哪里有问题"，断点是"看哪里有问题"。**

### 4.3 证据链：二分定位

当 bug 涉及多步流程时，不要从头 print 到尾，用**二分**：先看中间结果对不对，判断问题在前半段还是后半段，再对半缩小范围。

**不要对照 06.2 的代码找答案。** `课题06.2` 是正确版本，`课题06.3` 是埋了 bug 的副本——两者只差几行，任何 `git diff` 或文件对比器都会直接暴露全部答案。本课已经把"对照"通道移除了，你只靠复现脚本和调试工具。

### 4.4 防回归测试

```python
def test_calculate_db_uses_20_factor():
    sm = StateMachine()
    loud = np.ones(512, dtype=np.float32) * 0.5
    db = sm.calculate_db(loud)
    expected = 20 * np.log10(0.5 + 1e-7)   # 用公式算期望，不硬编码
    assert db == pytest.approx(expected, abs=0.01)
```

防回归测试的验收标准：**把 bug 改回来，测试必须红**。如果改回 bug 测试还是绿，说明你的测试没拦住它，等于没写。

## 5. 常见坑

### 坑 1：把"现象"当"根因"

```python
# ❌ 看到分贝值不对，直接调 db_threshold 阈值"补偿"
#    这是修现象，根因是公式错了

# ✅ 先问：分贝值本身算对了吗？用正确公式对照
```

### 坑 2：瞎试（没有假设驱动）

```python
# ❌ 改一个值跑一次，不行再改下一个——你只是在碰运气
# ✅ 先列出 2-3 个假设，然后设计一个实验排除其中一个
```

### 坑 3：修完不补测试

```python
# ❌ 改完代码，测试全绿，收工
# ✅ 补防回归测试，并把 bug 版改回来验证测试确实会红
```

### 坑 4：print 淹没代码

调试完不删 print，或者用 print 代替断点。print 会污染代码、污染输出，而且只能看到你预先想到要看的变量。

### 坑 5：用 git diff / 文件对比器去对照 06.2 目录

两个目录只差几行，一对比答案全出来了。本课的训练价值就在"不知道答案时用证据定位"——对照 = 跳过练习 = 课白上。

### 任务 2：逐个定位并修复（支架提示）

**Bug A —— 分贝值异常偏大（静默失效）**

- 现象：同一段音频，算出来的分贝比正确公式大 27dB 左右
- 排查方向：在 `calculate_db` 里断点，分别看 `rms` 和返回值；RMS 的定义是 `sqrt(mean(x^2))`，把每一步拆开对照
- 思考：为什么原有测试没抓住它？（提示：06.2 的测试根本没碰过 `calculate_db`）

**Bug B —— 语音段顺序倒置（逻辑反转）**

- 现象：完整语音段里，后说的话跑到前头去了
- 排查方向：在 ACTIVE 分支里断点，每次帧到达后看 `bytes_buffer` 的值，观察新块被加到哪一边
- 思考：`+=` 和 `x = y + x` 看起来都像"追加"，实际顺序完全相反

**Bug C —— 非法配置放行（契约不匹配）**

- 现象：`db_threshold=5`（正分贝）通过 Pydantic 校验，而它物理上没有意义
- 排查方向：在 `config.py` 里对比 `db_threshold` 和其他字段的约束写法（`prob_threshold` 有 `ge/le`，`required_hits` 有 `gt`）
- 思考：校验约束也是契约的一部分——测试测了 `prob_threshold` 和 `required_hits`，为什么没测 `db_threshold`？

### 任务 3：补防回归测试
